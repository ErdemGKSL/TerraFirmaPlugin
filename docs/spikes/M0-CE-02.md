# M0-CE-02: Per-block data store decision

**Status:** done (2026-10-16), all four targets (Paper and Folia, 1.21.11 and 26.3).

## Setup
- `spikes/ce-02/`: the same toy crop kept two ways, in one chunk area of 10 000 blocks (2 × 25 chunks):
  - **(a)** a CE `BlockEntityController` (`CropBe`) holding a planted tick, with NBT save/load. No ticker.
  - **(b)** our own per-chunk store (`PdcStore`): an in-memory map, serialised into the chunk PDC on unload and before save.
- Boot 1 places 10 000 blocks of each kind on their owner regions, unloads, waits 75 s, and saves. Boot 2 reloads and verifies, then runs destructive tests: a creeper-like explosion, a WorldEdit-like `setType(AIR)` run, a piston push, and `/ce reload`.
- Runner: `spikes/ce-02/run.sh` (`TARGETS=...` selects platforms).

## Results
Numbers from Paper 26.3 (other targets agree within the same order of magnitude; see `logs/ce02-<target>.txt`):

| Measure | (a) CE BlockEntity | (b) Chunk PDC store |
|---|---|---|
| place 10 000 blocks, region time | 237.6 ms (23.8 µs/block) | 38.2 ms (3.8 µs/block) |
| save | 3.5 ms (10 000 `saveCustomData`) | 10.6 ms (50 encodes, 25 chunks ×2) |
| load 25 chunks, decode only | 2.8 ms (`loadCustomData`) | 9.1 ms |
| load 25 chunks, wall time | 1591 ms | 458 ms |
| heap per block (noisy) | ~259 B | ~89 B |

Range over the four targets: (a) place 21–42 µs/block, (b) 4–10 µs/block; (a) decode 2.8–27 ms, (b) decode 4–20 ms. Load wall times are dominated by chunk loading, not by our code.

Behaviour after destructive operations (counts of blocks, 10 000 total):

| Operation | (a) result | (b) result |
|---|---|---|
| after restart, before any change | 10 000 ok | 10 000 ok |
| explosion (radius 4) | 55 blocks lost with their BE (`onRemove` = 55), rest ok | 56 orphan store entries left behind, rest ok |
| `setType(AIR)` ×10 by a vanilla path | `onRemove` = 10, no wrong data | 66 orphan entries in total |
| piston push of one crop | Paper 26.3 / 1.21.11: `piston_head` at the source, the controller moved with the block; Folia 26.3: crop_plain moved and became `stone` | `store[to]` stays null, `store[from]` still 42 |
| `/ce reload` with everything loaded | 9 935 ok, 0 wrong, the same 65 missing | 9 934 ok, orphans unchanged |

Thread checks: `threadViolations = 0` on all targets. Controllers were constructed on the region/worldgen threads, as M0-CE-01 showed.

## Decision
- **Use CE block-entity controllers for anything that has state and is placed by a player or a device** (crops planted by players, devices, inventories). CE removes the entry with the block (`onRemove`), so no data survives the block. Its data also goes through CE's own chunk storage, so it saves and reloads with the chunk. The cost is about 3–5× the write time and roughly 3× the heap per block in these runs, which is acceptable for player-placed blocks.
- **Use block properties only for wild worldgen blocks** (plants, ores, loose rocks) — no store at all. "No data" means wild/mature, as the ledger already says.
- **Our chunk-PDC store is rejected for per-block data.** It leaves orphan entries after every destructive path (explosions, vanilla `setType`, pistons), and cleaning them needs a per-block hook that CE already provides. It might still hold chunk-scale data (climate cache, support maps), as the architecture says, but never per-block state that a block can lose.
- The `/ce reload` result is safe for both: no data loss, no wrong state. Production guidance stays "restart, don't reload" (the controllers hold no config references, see the skill).

## Open / UNVERIFIED
- Piston behaviour differed between Paper and Folia 26.3 (the moved block: controller kept on Paper, stone on Folia 26.3). Both look like CE's piston handling of a block that has a controller; the Folia run used a different piston orientation. Treat piston movement of controller blocks as "needs a dedicated test" before M3 crops rely on it.
- Memory numbers are from `Runtime` heap deltas with GC noise; use them for order of magnitude only.
