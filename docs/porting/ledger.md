## Divergences

| TFC behaviour | Our behaviour | Reason | Revisit? |
|---|---|---|---|
| Player inventory has calendar/nutrition/climate tabs | Clicking outside the inventory window (fake button drawn by the resource pack) opens our TFC GUI | The player inventory screen can't be modified without a client mod | No |
| Client colormaps tint grass/foliage by climate + season | Custom biomes (datapack colours) + async biome-id rewrite in chunk packets per season | Tint is computed client-side | Maybe, if a better technique appears |
| Custom HUD overlays | BetterHud | No client mod | No |
| Ambient particles (steam, smoke, etc.) | Particles only on explicit player actions | Client/server performance | No |
| Custom fluids placed in the world (salt water, molten metal, river flow visuals) | Vanilla water/lava visuals + server-side behaviour, or placement disabled | Clients can't receive new fluid types | When a feasible technique appears |
| Ore blocks: 3 grades × ore × rock each with its own texture | Profile-dependent (ARCHITECTURE §9.1). Default 1.21.x `level-3a`: poor/normal share a visual, rich distinct. Default 26.x `level-2`: all grades distinct | Vanilla-client visual state budget, leaving room for other CraftEngine packs | Owner-configurable |
| Gem ores (amethyst, diamond, emerald, lapis, opal, pyrite, ruby, sapphire, topaz) look like ore in rock everywhere | From `level-2`: look like their host rock until exposed to air, then show an overlay (display entity) | Visual budget; bonus anti-xray | Owner-configurable |
| Deposits (gravel per mineral × rock) | From `level-2`: one gravel+specks visual per mineral, rock-agnostic | Visual budget | Owner-configurable |
| Wood/stripped wood blocks have per-axis models | From `level-1`: all axes share one visual (bark on all faces) | Visual budget | Owner-configurable |
| Metal blocks, mechanical blocks, crates, workbenches are block models | Drawn with `entity_renderer` display entities | Visual budget (approved) | No |
| Raw/hardened rock drops the raw block when mined while isolated (`tfc:is_isolated` loot condition) | Always drops 1-4 loose rocks | The condition needs our own CE loot condition; not ported yet | Yes, with rock collapse work |
| Mojang/NeoForge codecs ignore unknown JSON keys; Gson keeps the last of duplicate keys; JSON parsing is lenient | Our data loader rejects unknown keys, duplicate keys and non-strict JSON, and fails the whole load (all errors listed) | Catch datagen and hand-override mistakes at build time (M1-REG-04 test) instead of silently ignoring data | No |
| Ingredient JSON arrays hold vanilla values only | Arrays may hold any ingredient type | Superset; all TFC data parses unchanged | No |
| `PreciseIngredient.modifyStackForDisplay` (heat/rot/trait shown on JEI stacks) | Not in core; display stacks are a recipe-viewer/GUI concern | No JEI on vanilla clients; our GUIs add it when needed | When a recipe viewer GUI is built |
| `RemoveDyeModifier` clears the dye on the input stack and returns it | Hook returns a dye-less copy; inputs are never mutated | Inputs are snapshots under our threading model | No |
| Lava + water and other vanilla mechanics create cobblestone, obsidian, concrete, oxidised copper, dead coral, grass, moss, clay, sponge as usual | In TFC worlds, every vanilla block the visual allocation repurposes is never created: lava + water makes vanilla `stone` instead; hardening, oxidation, scraping/waxing, coral death, spread, bone meal and placement of those blocks are cancelled; they are stripped from drops and loot and from crafting/smelting results; `/setblock`/`/fill` and dispensers best effort | Their client-side look is one of our blocks (ARCHITECTURE §9.1); a real instance would look like TFC content | When the generator marks TFC worlds (M2), and if TFC's own lava + water result is ported |
| Custom sky / star map | Not implemented (optional core-shader work later) | Needs core shaders | Optional |
| NeoForge ships the `c:` common tags (`c:cobblestones`, `c:feathers`, ...) and `minecraft:milk`; TFC's data references them and only adds members to some `c:` tags | Datagen exports every `c:`/`minecraft:` tag file TFC has (TFC's additions only, not NeoForge's or vanilla's members). The 16 `c:` tags (and 12 vanilla tags) TFC references but never defines are listed in `data/external_tags.json`, generated from the references core's loader finds; the loader accepts exactly those undefined tags. Vanilla/NeoForge ids used by the data are listed in `id_map.json` `external_ids` the same way. Their members are not invented | The checkout has no NeoForge or vanilla tag/registry data. Member resolution of external tags (on a vanilla Paper server) belongs to the runtime tag bridge | Yes, when tags are wired to Paper's tag registries |
| Minecraft versions other than 1.21.11 and 26.3 are not supported (the `compat.yml` supported set) | Not supported. 1.21.1-1.21.3 are refused at startup by the `LifecycleEvents.DATAPACK_DISCOVERY` bootstrap (added in 1.21.4). 1.21.4-1.21.10 are refused in practice: BetterHud 2.2.0-SNAPSHOT-449 is Java 25 bytecode (class file 69), which the Paper 1.21.4 plugin remapper cannot read, so BetterHud never loads there (seen in-server 2026-10-17) | No server or CI run on those versions; the three client plugins and the bootstrap rely on 1.21.11+ | When BetterHud ships a build the 1.21.4 remapper can read, or the bootstrap drops DATAPACK_DISCOVERY |
| Calendar advances by `float` partial ticks (`calendarPartialTick += 20f / dayLength`) and `setMonthLength` uses a float fraction | Exact integer carry: `partialNumerator` counts 1/dayLength of a calendar tick, so advancing by `n` equals `n` single steps exactly (lazy == stepped). `withDaysInMonth` uses an exact integer fraction | Float drift makes lazy and stepped evaluation disagree over long spans; ARCHITECTURE §4.1 requires them to agree | When TFC changes its calendar arithmetic |
| `defaultCalendarStartDay = -1` (a valid TFC config value) produces negative calendar ticks; `ICalendar` getters then return meaningless fields | Config value rejected (`CalendarState.initial` throws); calendar ticks before January 1, 1000 are refused by `CalendarTicks` | Negative ticks have no defined date; the Paper config loader should report this as a config error (M2-CAL-01 glue) | Yes, when the calendar config is wired |
| `/time set hour N` moves `N * 0.041666f` of a day as float, so the target can be one calendar tick short of the hour boundary (`set hour 1` from midnight moves 999 ticks, not 1000) | The hour boundary is exact: `N * 1000` calendar ticks (24 and 0 both mean midnight, as in TFC) | Float rounding in a debug command; an exact boundary is what the command means | When TFC changes the command |
| `/time` skips advance player ticks by `calendarTicks / (20 / dayLength)` in float (`ServerCalendar.skipForwardBy`) | Player ticks advance by the integer floor of `calendarTicks * dayLength / 20`; the calendar ticks are exact | Same reason as the calendar carry above (exact integers, lazy == stepped) | When TFC changes its calendar arithmetic |
| `/time set dayLength`, `/time set monthLength`, `/time set rain`, `/time set clear` (TFC `TimeCommand`) | Not implemented. Day and month length are config (M2-CAL-01 follow-up), weather needs the climate and rain model | Not ported yet, so the command tree has no such literals | M2-CAL-01 config follow-up; M2-CLIM-01 and M2-WTH-01 |
| HUD date and season are translated by TFC's lang files (`tfc.tooltip.*`, month and season names) | `tfp_date` and `tfp_season` are English text (`June 1, 1000`, `Summer`) on every client | Our placeholders are server-side strings; per-player translation needs a text per locale in the HUD pack | When per-player HUD text is designed |
| TFC computes the climate from chunk data (`ChunkData`: average sea-level temperature, rainfall, rainfall variance, groundwater), generated by the region generator | Until M2-GEN-05, every chunk uses `ChunkClimate.NEUTRAL` (20 C sea-level average, 250 mm rainfall, no variance, no groundwater), so the HUD ambient temperature and `/tfp debug chunk` show the model's values for a temperate chunk, not the TFC world's | Chunk data does not exist yet. The readout is wired end to end so that real chunk values only replace the input | M2-GEN-05 |
