## 1. TL;DR

- **YAML is pre-processed at parse time** by a custom SnakeYAML-engine constructor. It handles `$$` version keys, `::` deep keys, duplicate-key merging, and extra numeric and array tags. This happens once per file. The parsed map is cached by mtime and size. [SRC `core/…/config/yaml/StringKeyConstructor.java`; `APM:579-632`]
- **Templates are expanded on every load, for every entry of every id-keyed section** (items, blocks, recipes, loot, …). Expansion runs whether or not the entry uses a template. Every string is scanned for `${…}`. [SRC `core/…/config/IdSectionConfigParser.java:32-67`]
- **config_factory = instances × blueprint.** Each instance becomes an argument map. Every top-level section of the blueprint is re-submitted to its normal parser with those arguments. `${}` in ids is resolved only in this path. [SRC `APM:3919-3972`]
- **Stage order:** `templates` → `config factories` → everything else (in parallel, following a dependency DAG). Templates therefore cannot be generated by a factory, and nested factories are ignored. [SRC `core/…/config/lifecycle/LoadingStages.java`, `LoadingPyramid.java:25-33`]
- **Section parsers that are not id-keyed ignore template arguments.** Examples are `lang`, `translations`, `block_state_mappings`, and `damage_rules`. A `lang:` block inside a factory blueprint is **not substituted**. (INFERRED from `SectionConfigParser.java:30-39`.)
- **There is no config-generation scripting.** The JS engine is runtime-only: events, tasks, placeholders, and `type: js` functions and conditions. Global variables are MiniMessage `<global:id>` text macros, not config macros.
- **Major source bug at b3079c5:** an entry with `enable: false` in any id-section parser `return`s out of the whole `loadAll()`. Every remaining entry of that type, and every already-collected entry, is then never parsed. [SRC `IdSectionConfigParser.java:72-74`] Never emit `enable: false`.
- **Recommendation (my opinion):** expand the matrices in **our datagen** into one small literal entry per id. Each entry references **our own `tfc:` templates** for the bulky shared structure (block-state shapes, settings, loot). Emit `lang` literally. Avoid `config_factory` for shipped content. Do not depend on `default:` templates at runtime; copy what we need into the `tfc:` namespace.

## 2. YAML extensions

All in `StringKeyConstructor` [SRC `core/…/config/yaml/StringKeyConstructor.java`]. It is used for every `.yml`/`.yaml` under `configuration/` and for `pack.yml` [SRC `APM:516-519, 634-680`].

### 2.1 `$$` version-conditional keys

| Form | Meaning | Source |
|---|---|---|
| `$$>=X` / `$$>X` | server version ≥ / > X | L181-183 |
| `$$<=X` / `$$<X` | server version ≤ / < X | L184-186 |
| `$$X` | **exactly** X (so `$$1.21` = 1.21.0 only) | L187-188 |
| `$$A~B` | A ≤ version ≤ B (inclusive) | L190-193 |
| `$$fallback` | Only in a *value selector* (below) | L213-216 |

Version parsing is `VersionHelper.parseVersionToInteger` [SRC `core/…/util/VersionHelper.java:131-164`]. It reads up to three dot-separated parts as `10000*a + 100*b + c`, so `1.21.11` = 12111 and `26.1` = 260100. **It skips every character that is not a digit or a dot.**

Two behaviours follow:

1. **Merge mode.** In a mapping that mixes `$$` keys with normal keys, a matching `$$` key's value must be a **map**. It is deep-merged into the parent (L104-112, `mergeMap` L159-175). A non-map value, or a non-matching key, is silently dropped. `$$fallback` in a mixed map never matches, because "fallback" parses to 0, and it is silently ignored.
2. **Value-selector mode.** If **every** key of a mapping starts with `$$` (L197-205), the whole node is replaced by the value of the matching key. Any type is allowed. **The last match wins** (L217-219). If no key matches, or the matched value is `null`, `$$fallback` is used (L221).

```yaml
# CFG default_feature_populator/pack.yml – value selector picks a whole map
subpacks:
  $$>=26.3:
    26_3: true
  $$26.1~26.2:
    26_1: true
  $$fallback:
    fallback: true
```
```yaml
# CFG default_assets/configuration/items/hami_melon.yml – merge mode (excerpt quoted in craftengine.md §4.2)
data:
  item_name: <!i><lang:item.default.hami_melon_slice>
  $$>=1.20.5:
    food: { nutrition: 2, saturation: 1.0, can_always_eat: false }
```

**`#tag` uniqueness.** YAML forbids two identical keys. You can write `$$>=26.3#default:palm_tree:` and `$$<26.3#default:palm_tree:` [CFG `default_assets/configuration/blocks/tree.yml` L715, L773 (`configured_feature:`)]. No code strips the `#…`. It "works" only because the version parser ignores letters, `:` and `_`. **A tag containing digits or dots corrupts the version.** For example, `$$>=1.21.4#rock2` parses as 1.21.**42**, and `#a.b` shifts the parts. Use tags made only of letters and `_`/`:`/`-`. (INFERRED from VersionHelper L137-153.)

### 2.2 `::` deep keys
`a::b::c: v` is the same as `a: {b: {c: v}}`. It is split on every `::` (L115-138). Intermediate maps are created or reused. If an intermediate key already holds a non-map, a warning `yaml.inconsistent_value_type` is logged and the value is **replaced** (L128). Keys that start with `$$` are handled as version keys first (L93-97). A `::` inside a `$$` key is therefore not split, and **any other key containing `::` is always split.** Shipped usage includes `loot::template: default:loot_table/self`, `settings::map_color: …` [CFG tree.yml L61-63], and `arguments::block_type: grass` [CFG default_templates/…/block_settings.yml L185].

### 2.3 Duplicate keys
SnakeYAML's own duplicate check is bypassed, because `constructMapping` is overridden (L84-102). Rules (`setValueWithDuplicationCheck` L146-156):
- When both values are maps, they are **deep-merged silently** with no warning.
- Otherwise the later value wins and `yaml.duplicated_key` is logged: `"Found duplicated key '<key>' at line <n> in file <path>"` [CFG translations/en.yml L168].

(Correction to craftengine.md, which said map merges warn.)

### 2.4 `#suffix` on section names
In `processConfigEntry` the text after the first `#` of a **top-level** key is dropped to find the parser. `items#0`, `config_factory#basic` and `templates#sounds` all work [SRC `APM:757-767`; WIKI `/configuration`]. Only top-level keys whose value is a map are considered. **An unknown top-level key, such as a typo like `itmes:`, is silently ignored** (L762-765).

### 2.5 TAB fixing
If parsing fails with a ScannerException mentioning `TAB` and `indentation`, every `\t` is replaced by 4 spaces. The file is re-parsed and, on success, **rewritten on disk** [SRC `APM:650-668`]. This changes mtime and content, which would trip our hash manifest. Never emit tabs.

### 2.6 Tags and scalars
- Extra tags are `!!byte !!short !!long !!double !!ByteArray !!IntArray !!LongArray !!DoubleArray !!IntList !!LongList !!DoubleList`, plus `!!binary`. The UUID tag is also registered, but **UNVERIFIED** how to write it in YAML. [SRC StringKeyConstructor L27-61; constructors in `yaml/constructor/*`]
- Plain floats become **Double** (tag `!!double` via `DoubleSensitiveScalarResolver`). Plain ints become int, or long if large. `0x…` and `0o…` are accepted. Bools are `true/True/TRUE/false/…` only. [SRC `yaml/DoubleSensitiveScalarResolver.java:12-38`]
- A plain scalar that looks exactly like `${word}` or `${word:-word}` is resolved to SnakeYAML's ENV tag (L13, L37). Shipped files rely on it being returned unchanged, for example `fuel_time: ${wood_fuel_time:-300}` [CFG tree.yml L47]. INFERRED: the engine's env constructor returns the raw string when no EnvConfig is set. Quoting placeholders is never wrong.
- **Numeric config fields accept arithmetic strings.** `ConfigValue.getAsInt` falls back to `Expressions.evaluate` [SRC `core/…/config/ConfigValue.java:119-139`], hence `fuel_time: "${wood_fuel_time:-300} / 3"` [CFG tree.yml L166].

### 2.7 JSON configs
`.json` files under `configuration/` are loaded with Gson into a `Map<String,Object>` [SRC `APM:600-606, 682-693`].
- No `$$`, `::` or duplicate merging is applied. Templates still apply, because they run later on the map.
- INFERRED: Gson's default policy turns every number into a `Double`. Fields read with `getAsInt` still work. Anything that checks for an exact `Integer` type, such as typed SNBT or component data, may differ from YAML.
- No shipped JSON config exists.

## 3. Templates

Implementation: `TemplateManagerImpl` [SRC `core/…/config/template/TemplateManagerImpl.java`]. Wiki: `WIKI /reference/template`.

### 3.1 Definition
```yaml
templates:            # also "template", "templates#x", kebab variants (ConfigKeys.of("template(s)"))
  tfc:settings/rock:  # id; namespace defaults to the pack namespace
    hardness: ${hardness:-1.5}
    …any YAML (map, list or scalar)
```
- The parser is an `IdValueConfigParser` [SRC L42-80]. Template bodies are only **pre-parsed** (strings become `ArgumentString` trees) and stored in a `ConcurrentHashMap<Key,Object>` (L25, L66-68). They are **not** expanded at definition time (`createConfigValue` override, L76-79).
- Ids are global across all packs. A duplicate id gives `resource.duplicated_id` and the **first one registered wins** [SRC `IdConfigParser.java:9-16`]. Registration order follows file-walk order, which is OS-dependent.
- **Reference resolution:** `template: foo/bar` without a namespace resolves to **`minecraft:foo/bar`**, not to the pack namespace [SRC `TemplateManagerImpl.java:276`; `core/…/util/Key.java:44-46`]. Always write fully qualified ids.

### 3.2 Use forms
Any map anywhere inside an id-keyed entry that contains `template` (or `templates`) is a template call [SRC L124-129]. The reserved keys are `template(s)`, `arguments`, `overrides` and `merges` (L18-23). Other keys beside them are treated as extra merges (§3.3).

```yaml
settings:
  template: tfc:settings/rock                    # single id
states:
  template: [tfc:a, tfc:b]                       # list – processed in order
  arguments: { texture: tfc:block/rock/raw/granite }
  overrides: { … }                               # replace
  merges:    { … }                               # deep merge
loot::template: default:loot_table/self          # with :: deep key
```
- Template ids may themselves contain placeholders: `template: default:block_state/${leaves_tint_type}_leaves` [CFG default_templates/…/block_states.yml L81].
- **An id that resolves to `null` is skipped** [SRC L274-275]. This allows conditional inclusion through a `condition`/`when` argument whose result is null. INFERRED.
- An unknown id throws `resource.template.invalid_template`: "Invalid template '<id>'" [SRC L276-279; CFG en.yml L303].

### 3.3 Combination rules (`processMap` L118-215, `processTemplates` L246-335)
Let T₁…Tₙ be the expanded templates. The type of **T₁** decides the mode:

| T₁ type | Combine templates | `overrides` | `merges` / extra keys |
|---|---|---|---|
| Map | `deepMergeMaps` in order (non-map templates are ignored) | **shallow** `putAll` (top-level keys replaced wholesale) | deep merge (applied **after** overrides) |
| List | concatenate lists (non-list templates are ignored) | if a list: **replaces** everything | if a list: appended |
| Scalar | **last** template wins | if present: returned | else if present: returned |
| (no template resolved) | – | map: copy + deep-merge merges; list: copy + append merges; else overrides, else merges, else `null` | |

`deepMergeMaps` (L374-397) works like this:
- map + map recurses.
- **list + list concatenates (append).**
- Anything else is replaced by the later value.
- **Odd case:** a key in the merged map that starts with `$$` (only reachable via escaping, e.g. `\$\$key`) is stored with one `$` stripped and not merged. The purpose is undocumented (UNVERIFIED).

**Extra keys** beside `template`: if the call map has keys other than the four reserved ones, they are evaluated and put into a `merges` map. Then an explicit `merges:` map is `putAll`-ed over them (shallow) (L305-326). Example: `default:settings/sapling` puts `burnable: false` next to `template:`/`overrides:` [CFG block_settings.yml L14-25]. The effective order is: templates → overrides (shallow) → extras+merges (deep).

The wiki's wording is: "overrides fully replaces … merges deeply combines … including lists" [WIKI /reference/template]. That matches the code.

### 3.4 Argument scoping and precedence (important, undocumented)
`mergeArguments` (L339-363):
- Child `arguments:` are merged into a **copy** of the parent scope.
- **The parent (outer) argument wins:** `if (result.containsKey(placeholder)) continue;` (L349). A template that sets `arguments: {x: 1}` for an inner template is overridden by any `x` coming from the caller or the config_factory instance. This is how `${leaves_tintable}` from an instance reaches `default:block_state/leaves`. It also means **an inner template cannot shadow a name used by an outer caller**, so use distinct, prefixed argument names.
- `__NAMESPACE__` and `__ID__` are always in the root scope and can never be overridden.
- Child argument **values are evaluated in order against the scope built so far**, so a later argument can use an earlier one, and also any parent argument (L350; WIKI "applied sequentially").
- Argument **keys** may contain placeholders (L345).
- The evaluated value decides the argument kind (L351-360):
  - a map with a `type` → typed argument (§5)
  - another map → `map`
  - a list → `list`
  - `null` → `null`
  - anything else → `object` (raw value, type preserved)

### 3.5 Nesting
Templates may use templates without a fixed depth limit. Example: `default:block_state/leaves` → `…/tintable_leaves` → `…/__leaves__` [CFG block_states.yml L80-97]. Recursive self-reference has no guard. INFERRED: it ends in a `StackOverflowError`, which surfaces as an "Unknown error type" with a stack trace.

### 3.6 Where templates apply
- Applied: every id-keyed parser (`IdSectionConfigParser`/`IdValueConfigParser`): items, blocks, furniture, recipes, loot, loot_sources, categories, images, emoji, sounds, jukebox songs, paintings, advancements, entities, attributes, equipments, configured/placed features, atlases, **global variables**. Each entry gets root args `__NAMESPACE__`/`__ID__` [SRC `IdSectionConfigParser.java:47-61`; `IdValueConfigParser.java:58-70`].
- Not applied: `SectionConfigParser` types, which are `lang`, `translations`, `block_state_mappings`, `damage_rules`, `skip_optimization` and `config_factory` itself [SRC `SectionConfigParser.java:30-39`; parser classes listed via `grep "extends SectionConfigParser"`].
- Debug aid: put `debug: true` in an id-section entry and CE logs the **fully expanded entry as JSON** [SRC `IdSectionConfigParser.java:75-77`].

## 4. Placeholder grammar

Implementation: `ArgumentString.preParse` and `Placeholder` [SRC `core/…/config/template/ArgumentString.java`]. Every string scalar **and every map key** in every id-keyed entry goes through `preParse` [SRC `TemplateManagerImpl.java:99-115`].

| Syntax | Meaning | Source |
|---|---|---|
| `${name}` | value of argument `name`. Missing → error `resource.template.missing_argument` | L110-122 |
| `${name:-default}` | default used when the argument is absent. Split at the **first** `:-` | L67-87 |
| `${name^}` | `StringUtils.capitalize`, JVM default locale (the wiki says it capitalizes each word) | L88-97, L123-125 |
| `${name^^}` | `toUpperCase(Locale.getDefault())` | L89-92, L126-128 |
| `\$` (outside a placeholder) | literal `$` | L367-370 |
| `\{` `\}` (inside a placeholder) | literal braces | L329-337 |
| nesting `{…}` inside `${…}` | brace depth is tracked, so `${a:-"${b}"}` works | L321-356 |
| unterminated `${` | treated as literal text | L358-364 |
| built-ins | `${__NAMESPACE__}`, `${__ID__}` of the **enclosing entry** | IdSectionConfigParser L47-61 |

There is **no lower-case modifier**. Use the `to_lower_case` argument type.

**Defaults are SNBT** (`TagParser.parseObjectFully`) and are themselves pre-parsed, so they may contain placeholders.
- `${count:-1}` gives an int and `${hardness:-3.0}` a number.
- Quote strings that contain `:`/`.`/`#`/`<`: `${rotate_sound:-'minecraft:block.bamboo.place'}` [CFG events.yml L11], `${default_leaves_color:-"#48B358"}` [CFG tree.yml L215], `${category_name:-"<white>${namespace}:${tree_type}"}` [CFG tree.yml L39].
- `${x:-null}` makes the placeholder evaluate to `null` [usage CFG events.yml L55; code L78-80, L116-118]. In a map key, null removes the key [TemplateManagerImpl L207-211]. As a value it stores `null`.
- The `TagParser` source is **not in the repository** (imported from `core.util` but absent), so exact SNBT typing rules are UNVERIFIED. For example, it is unknown whether `true` becomes a boolean or a byte.
- A bad default gives `resource.argument.parser.snbt` at construction.

**Return types:**
- A string that is **exactly one placeholder** returns the argument's **raw object**: a map, list, int, etc. [L382-384].
- Mixed text concatenates `String.valueOf` of the parts.
- Edge cases (L166-226):
  - With two parts, both null → `null`, and one null → the other part as a String.
  - With three parts, all null → `""` (not null).
  - With four or more parts, all null → `null`.

## 5. Template argument types

Registry: `TemplateArguments` [SRC `core/…/config/template/argument/TemplateArguments.java:16-63`].
- `type:` values are resolved with `Key.ce(type)`, so `type: plain` = `craftengine:plain`.
- An unknown type gives `resource.template.unknown_argument_type` (L57-59).
- A map that has a String `type` key is a typed argument, unless it contains `__skip_template_argument__`. In that case it is a plain map, and INFERRED: the marker key is passed through into the output (L51-55).
- Kebab-case aliases (`value-type`, `step-interval`) are accepted, because keys go through `ConfigKeys.of` [SRC `core/…/config/ConfigKeys.java`].

|---|---|---|---|
| *(implicit object)* | any scalar | raw value, type preserved | `ObjectTemplateArgument` |
| `object` | `value` | raw value of `value` | `ObjectTemplateArgument.java:27` |
| `plain` | `value` (default `""`) | always a String | `PlainStringTemplateArgument.java:20` |
| `map` | `map` or `value` (required) | that map, by reference | `MapTemplateArgument.java:18-21` |
| *(implicit map)* | a map without `type` | that map | TemplateArguments L52-53 |

Because typed-argument maps are evaluated *before* the factory runs (TemplateManagerImpl L350-353), `condition: ${leaves_tintable:-false}` and `source: "${part}"` work in template `arguments:`.

Examples, from the wiki [WIKI /reference/template] and shipped files:
```yaml

  damage: { type: expression, expression: "${base_damage:-10d} * ${damage_multiplier:-1d}", value_type: double }
  leaves_tint_type:            # CFG default_templates/…/block_states.yml L83-87
    type: condition
    condition: ${leaves_tintable:-false}
    on_true: tintable
    on_false: non_tintable
  slot: { type: when, source: "${part}", when: { helmet: head, chestplate: chest }, fallback: any }
  tier.uppercase: { type: to_upper_case, value: "${tier}", locale: en }
  extra:                       # a literal map whose content has a 'type' key
    __skip_template_argument__: {}
    type: minecraft:constant
    value: 0
```

## 6. config_factory

Implementation: `ConfigFactoryParser` [SRC `APM:3919-3972`]. Wiki: `WIKI /reference/template#config-factory`.

```yaml
config_factory#rocks:            # ConfigKeys.of("config_factor(y|ies)") – also config-factory, config_factories
  instances:                     # aliases: instance, input(s)  (non-empty list of maps)
    - rock: granite
      category: igneous_intrusive
    - rock: basalt
      category: igneous_extrusive
  blueprint:                     # aliases: prototype, schema  (required map)
    items:
      tfc:rock/raw/${rock}: { … }
    blocks#x:
      tfc:…: { … }
```

### 6.1 Exact semantics (L3930-3946)
1. For **each instance**, a new `HashMap<String,TemplateArgument>` is built with `TemplateArguments.fromConfig(value)` for every key (§5). Instance values are **not** placeholder-evaluated. They cannot refer to each other, and `${x}` inside an instance value stays literal text. This differs from template `arguments:` (§3.4).
2. For each top-level key of `blueprint` (`items`, `blocks#2`, `recipes`, …), with null values skipped, `processConfigEntry(key, value, path, pack, args)` is called. That is exactly what happens for a normal file, except that the instance argument map is attached (L757-767).
3. Later, each id parser expands the section **once per instance**. It **resolves `${}` in entry ids only when arguments are present and the id contains `$`** (`IdSectionConfigParser.java:39-41`). The id becomes `Key.withDefaultNamespace(resolvedKey, pack.namespace())` (L42). Then `__NAMESPACE__`/`__ID__` are added to the instance map and templates are applied (L47-61).
4. The parser's `count()` is the number of factory **sections**, not instances (L3945).

### 6.2 Interactions and limits
- **Ordering:** CONFIG_FACTORY depends on TEMPLATE. All non-core stages implicitly depend on CONFIG_FACTORY [SRC `LoadingPyramid.java:25-33`, `APM:3963-3971`]. Blueprints may therefore use any template. **A `templates:` section inside a blueprint is too late** and is ignored, because the TEMPLATE stage has finished (INFERRED). **A nested `config_factory` inside a blueprint is ignored**: the factory parser's `loadAll` iterates a size captured beforehand (`SectionConfigParser.java:4-29`). INFERRED.
- **Sections without templates:** `lang`, `translations` and `block_state_mappings` in a blueprint are passed to parsers that ignore arguments, so `${…}` stays literal (INFERRED, §3.6). The shipped tree factory has no lang block and uses `<lang:item.${namespace}.…>` keys defined elsewhere [CFG tree.yml L53].
- **Shared mutable argument objects:** one instance map is shared by every blueprint section of that instance.
  - `MiscUtils.init(arguments, …)` **mutates** that map to put `__ID__` per entry [SRC `IdSectionConfigParser.java:56-60`; `core/…/util/MiscUtils.java:93-96`].
  - Different parsers run on **different threads at the same time** (items, recipes, blocks, loot… are separate DAG stages).
  - So a blueprint with several section types shares one plain `HashMap` across threads. INFERRED risk: a wrong `${__ID__}` or a corrupt map.
  - Likewise a `self_increase_int` instance argument is shared and unsynchronized.
  - **Mitigation:** one section type per factory, and avoid `${__ID__}` in factory blueprints. Better, avoid factories (§11).
- **List and map arguments are returned by reference.** If a template's first map holds `tags: ${extra_tags}` and a later template or merge also has `tags: […]`, `deepMergeMaps` calls `existingList.addAll(…)` on **the argument's own list** [TemplateManagerImpl L385-388]. The list then grows for every later use in the same instance. INFERRED. Pass lists as the last contributor, or have datagen write them literally.
- **Error granularity:**
  - If an instance value has a bad typed argument, the **whole factory section** fails (exception inside `parseSection` → one issue on the factory node).
  - Errors inside expanded entries are reported against the factory **file** with node paths like `items.tfc:rock/raw/granite.…`. The instance index is not reported.
- **Performance:** the factory itself only builds argument maps. The real cost is template expansion inside each parser's **single-threaded first loop** (`IdSectionConfigParser.java:33-67`). Only `parseSection` afterwards is parallel (L84-101). See §9.6.

### 6.3 Shipped examples

  - `config_factory#basic` (L10-604): one instance (`palm`) produces a category, ~13 items (each with an inline block) and recipes.
  - `$$>=1.20.3:` `config_factory#extra` (L610-702) produces slab and stairs. The version gate wraps the whole factory.
- `internal/configuration/destroy_stages.yml` holds 10 instances `- stage: N` and a blueprint key `${namespace:-"minecraft"}:destroy_stage_${stage}`. A default in an id key works.

## 7. Global variables, expressions, custom argument types, JS scripting

### 7.1 Global variables, a runtime text macro and not a config macro
- Section `global_variable(s)`, stage GLOBAL_VARIABLE (non-core, after factories) [SRC `core/…/plugin/context/GlobalVariableManager.java:49-76`].
- Each value is stored as a String under **`id.value()` (the namespace is dropped)** (L68-70). `a:coin` and `b:coin` therefore collide silently, and the last one written wins. Use unique un-namespaced names.
- Used through the MiniMessage tag `<global:id>` or `<global:id:'arg0':'arg1'>`. The values may contain `<arg:0>` [SRC `core/…/text/minimessage/GlobalVariableTag.java:24-50`; WIKI `/configuration/global_variable`]. They are also sent to proxies (`NetworkTagDataSerializer`).
- Global-variable values go through the template engine (IdValueConfigParser). **A `${` inside a value must be escaped** (INFERRED).
- Not useful for config generation. Useful for a shared lore or name fragment, such as a TFC heat or rarity prefix.

### 7.2 Expressions
- `Expressions.evaluate` uses `net.momirealms.sparrow.expr.ExpressionCompiler` (sparrow-expression 1.0, external). Unknown identifiers are rejected [SRC `core/…/plugin/context/expression/Expressions.java:14-27`].
- The supported operators and functions are **UNVERIFIED**: the library is not in the clone. The wiki example uses `*` and `10d` literals.
- Used by `expression` arguments and by numeric field parsing (§2.6).

### 7.3 Custom template argument types (Java)
`TemplateArguments.register(Key, TemplateArgumentFactory)` is public and static [SRC `TemplateArguments.java:31-36`]. The factory receives the evaluated `ConfigSection` and returns `TemplateArgument.get(node, args)`. We could register, for example, `tfc:rock_prop` (`type: tfc:rock_prop`). **UNVERIFIED** whether a namespaced `type:` value is resolved by `Key.ce` (it keeps an explicit namespace if one is given; `Key.decompose` source not checked). Registration must happen before CE's first config load (our `onLoad`). CE delays config load by default (`misc.delay-configuration-load: true`, CFG config.yml L862).

### 7.4 JS scripting, runtime only
- Off by default: `scripting.js.enable: false`. `engine: nashorn` (~2.4MB) or `graaljs` (~68MB), `strict: true`, `nashorn-compat: false` [CFG config.yml L843-854; `core/…/config/Config.java:411-414`]. Restart required. The dependencies are downloaded on first enable [WIKI /reference/script].
- Scripts live in `<pack>/script/**/*.js` (and in subpacks). The id is `<pack-namespace>:<relative path without .js>` [SRC `core/…/plugin/script/ScriptManagerImpl.java:202-218`]. They load **after** all configs [SRC `CraftEngine.java:344-366`].
- Capabilities: comment annotations `//@Subscribe` (Bukkit events), `//@Enable`, `//@Disable`, `//@Task`, `//@Placeholder`, `//@RelationalPlaceholder`. Bindings are `log`, `scheduler`, `ctx` and `__script`. Called from YAML through `type: js` in **functions**, **conditions** and **damage formulas** (`script`, `function`, `args`) [SRC `ScriptManagerImpl.java:51-59`; `core/…/context/CommonFunctions.java:69`; `CommonConditions.java:47`; `core/…/attribute/formula/DamageFormulas.java:17`; WIKI /reference/script].
- **Security: none.** GraalJS contexts use `.allowAllAccess(true)` [SRC `GraalScriptEngine.java:46-54`]. Nashorn has full host access. Scripts are fully trusted code.
- **It cannot generate configuration.** Nothing hooks scripts into parsing. Irrelevant for our datagen decision. We have Java anyway.

## 9. Load pipeline

### 9.1 Sequence (`CraftEngine.reloadPlugin`, SRC `core/…/plugin/CraftEngine.java:304-415`)
All of the following runs on the async executor except the last step:
1. `config.load()`, then translations, then `reloadManagers()` (clears templates and globals). `scriptManager.unload()`.
2. `packManager.loadPacks()`: lists the direct sub-dirs of `plugins/CraftEngine/resources/` and reads `pack.yml` (§10) [SRC `APM:485-558`].
3. `updateCachedConfigFiles()`: for each **enabled** pack, `Files.walkFileTree` (follows symlinks) over `configuration/` and each enabled subpack's `configuration/`. It picks `.yml`, `.yaml` and `.json` (case-insensitive). If a file's **mtime and size** both match the previous cache, its parsed map is reused. Otherwise it is re-parsed. **This walk and the parsing are single-threaded.** Each top-level section is then dispatched to its parser via `processConfigEntry` [SRC `APM:579-632`].
4. `loadResources`: a `LoadingPyramid` DAG of `CompletableFuture`s on CE's async executor [SRC `APM:695-749`]. For each parser: `preProcess`, then `loadAll`, then `postProcess`, then the log line `Loaded <stage> in <ms>ms (<count>)` (only when count > 0) [CFG en.yml L276].
5. `clearResourceConfigs()`, then scripts load (`//@Enable`), then delayed tasks.
6. On the main thread, sync tasks register recipes, sounds, paintings, advancements and so on. `CraftEngineReloadEvent` is fired (fire-and-forget; it carries only `isFirstReload()`) [SRC `bukkit/…/api/event/CraftEngineReloadEvent.java`].

### 9.2 Stage DAG
[SRC `LoadingStages.java`; `dependencies()` overrides found by grep]
- `templates` (core) → `config factories` (core). **Every non-core stage also waits for config factories.**
- `equipments` → `items` → (`blocks` [+`block state mappings`], `recipes`, `furniture`, `categories`, `advancements`[+blocks]) …
- `images` → `emojis`, `lang`.
- `sounds` → `jukebox songs`. `loot tables` → `loot sources`. `blocks` → `configured features` → `placed features`. `attributes` → … .
- Independent stages run concurrently.

**Cross-file references are free:** all files are gathered before any stage runs, and templates are global. Cross-*type* references (a block referencing an item) rely on the DAG order above.

### 9.3 Inside an id parser
[SRC `IdSectionConfigParser.java:32-102`]
- Phase A is **sequential on the stage's thread**. For each collected section and entry it:
  - resolves the id
  - checks for duplicates (`resource.duplicated_id`: "Another file ('<path>') contains a section with the same ID", **first wins**)
  - runs `applyTemplates`
  - checks that the result is a map, else `Expected a configuration section, found '<type>'`
  - applies `enable` / `debug` (see the pitfall in §12)
  - queues the entry
- Phase B runs `parseSection` for every queued entry on the async executor when `misc.multi-threaded-configuration-load: true` (default) [CFG config.yml L864; `Config.java:405`]. Items, blocks and templates opt in through `async()` [SRC `AbstractItemManager.java:310, 369`; `AbstractBlockManager.java:447`; `TemplateManagerImpl.java:71-73`].

### 9.4 Error reporting format
Errors are collected per file (including `cause` chains) and printed after the whole DAG finishes [SRC `APM:698-748`]:
```
[WARN] Found <n> issue(s) in file '<absolute path>':
[WARN] [1] <node path, e.g. items.tfc:rock/raw/granite.behavior.block.states.template[0]> - <localized message>
[ERROR] [2] <node> - Unknown error type   + stack trace      (UnknownResourceException = non-Known throwable)
```
YAML syntax errors are logged earlier: `Invalid YAML file found: <path>.` or `Error found while reading config file: <path>`. The file is then skipped entirely [SRC `APM:669-679`].

**Programmatic detection:**
- `ReloadResult(success, asyncTime, syncTime, issues)` is returned by `CraftEngine.reloadPlugin(…)` [SRC `CraftEngine.java:219-226`]. That is internal API, and the event does not carry it.
- `/ce reload` prints `⚠ <n> issue(s) found` only to players [SRC `bukkit/…/command/feature/ReloadCommand.java:40-50`].
- The practical options are:
  - **(a)** our in-server self-test asserts that every expected id exists via `CraftEngineItems`/`CraftEngineBlocks` after `CraftEngineReloadEvent`.
  - **(b)** a log appender on CE's logger. On Paper the logger is an SLF4J logger from the bootstrap context [SRC `bukkit/paper-loader/…/PaperCraftEngineBootstrap.java:50-55`]. On the Bukkit loader it is the JUL `plugin.getLogger()` [SRC `BukkitCraftEngine.java:91-94`]. Match `Found .* issue\(s\) in file '…/resources/terrafirmacraft/…'`. The logger name is UNVERIFIED.
  - **(c)** best of all, **validate in datagen** so CE never sees a bad file.

### 9.5 Caching facts
- Only the **parsed YAML map** is cached, by path, mtime and size. It stays in memory for the server's lifetime (`cachedConfigFiles`).
- Template and factory expansion and all parsing are **redone on every reload**.
- A changed file is re-parsed alone. That favours **many medium files** over one giant file.
- Files are walked in OS order. The pack order is `DirectoryStream` order. Neither is sorted, so duplicate-id resolution is nondeterministic across machines.

### 9.6 How long do large packs take? (UNVERIFIED, no benchmarks found)
- No timing data was found in the repo or wiki. CE logs each stage's time, so measure it.
- INFERRED complexity: expansion is a recursive walk that allocates new maps, lists and strings for every node. A `stairs` template is about 685 YAML lines and expands into thousands of nodes. Using it for 200 blocks costs O(10⁵–10⁶) node copies on **one thread per stage**. My estimate is about 0.1–1 s. Literal YAML of the same size instead costs SnakeYAML parse time once at startup, single-threaded, roughly tens of MB/s, and is cached afterwards.
- Either cost is probably small next to resource-pack generation and image optimisation (UNVERIFIED).

## 10. pack.yml and subpacks

[SRC `APM:485-558`; `core/…/pack/Pack.java:24-33, 108-115`; WIKI `/configuration`]
- **Pack** = any non-hidden directory under `resources/`. The directory name must be a valid namespace to serve as the default namespace, else `minecraft`.
- `pack.yml` (optional) keys:
  - `enable` (true)
  - `namespace` (overrides the folder name). It is the **default namespace for un-namespaced ids in that pack's configs**.
  - `description`, `version`, `author`
  - `subpacks: {id: bool}`
- `pack.yml` is parsed with `StringKeyConstructor`, so `$$` works (value selector example in §2.1).
- Folders per pack: `configuration/`, `resourcepack/`, `blueprint/` (.bbmodel), `script/`. Each enabled subpack contributes `subpacks/<id>/<same folder>`, **main pack first**.
- The log line is `Loaded pack: <folder>. Default namespace: <ns>`.
- A YAML error in `pack.yml` is logged, and the pack still loads with its defaults.
- Usage for us: one pack `resources/terrafirmacraft/` with `namespace: tfc`. Version-specific content can go in subpacks selected by a `$$` value selector, e.g. `subpacks: {$$>=26.1: {v26: true}, $$fallback: {v1_21: true}}`.

## 11. Recommendation

**This section is the author's opinion, not CE documentation.**

### 11.1 Decision: expand matrices in datagen, share structure via `tfc:` templates
| Criterion | Literal entries from datagen (+ our templates) | CE `config_factory` |
|---|---|---|
| Debuggability | Errors point to `file + items.tfc:rock/raw/granite…`. `debug: true` per entry. Grep-able ids | Errors point to the factory file with no instance index. A bad instance argument kills the whole factory |
| Correctness risks | none beyond templates | shared mutable arg map across threads (`__ID__`), list-arg mutation, lang not substituted, nested factory and templates ignored, `${}` not evaluated in instance values |
| Load time | YAML parse once, then cached (mtime/size). Expansion of small template calls per reload | Tiny YAML. Same per-reload expansion (expansion is not cached either way) |
| Diff-ability (git, PR review, the hash manifest) | Every id has a stable line. TFC data changes produce small diffs | Changes in a blueprint affect hundreds of ids invisibly |
| User editability | A server owner can tweak or override one rock's block, or a template to affect all. Our manifest detects edits per file | Editing one instance is easy, editing one product is hard |
| Validation | Datagen can check ids, models, textures and state budgets before CE runs | Only CE's runtime log |

**Design:**
1. **Datagen emits one entry per id**, with only the *varying* data (ids, textures, numbers, drops). The entry delegates to templates:
   ```yaml
   # configuration/rock/granite.yml   (generated; one file per rock → minimal re-parse, clean diffs)
   items:
     tfc:rock/raw/granite:
       template: tfc:item/rock_block
       arguments:
         rock: granite
         block_kind: raw
         hardness: 6.5        # literal value from TFC data, no CE expressions needed
   ```
   Keep each argument scalar or a small literal. Datagen does all the computation (expressions, lookups, conditions), and CE does pure substitution.
2. **Our template library (`tfc:` namespace, shipped in our pack)**:
   - `tfc:settings/*`: copies of `default:settings/hardness/sound/burn_data` that we need, plus TFC material classes (rock, ore, soil, sand, gravel, wood, plant, crop).
   - `tfc:block_state/*`:
     - pillar, cube_all, cube_column
     - our own `auto_state`-based slab, stairs and wall (§8.1 limits)
     - an ore overlay
     - crop-stage and plant shapes
   - `tfc:loot_table/*`: self, ore-by-grade, rock-to-loose-rocks, crop-by-stage.
   - `tfc:item/*`: block_item wrappers, metal item families (ingot, sheet, double_sheet, tool heads…).
   - Prefix every argument with its template domain (`slab_texture`, `ore_grade`, …). The outer argument wins (§3.4), so generic names like `texture` collide.
   - Never put list arguments first in a list-merged key (§6.2).
3. **Emit `lang`/`translations` literally**, because templates do not apply to them.
4. **Do not use `config_factory` for shipped content.** Optionally document it for server owners who want to add a custom rock or wood themselves.
5. **Do not reference `default:` templates.** Re-author the ones we want in `tfc:`. The CE repository is GPL-3.0 (repo `LICENSE`), and our plugin is EUPL-1.2. Copying the YAML verbatim may make our pack a derivative work, so re-author it from the semantics documented here. The legal question is UNVERIFIED and needs a human decision.
6. **Use `$$` only where vanilla data formats differ** (1.21.x vs 26.x). Prefer datagen choosing per-version files through subpacks for large differences.
7. **Never emit:** tabs, `enable: false`, un-escaped `${` in text, `::` inside keys meant literally, `#tag` containing digits in `$$` keys.
8. **CI gate:** datagen runs a YAML lint plus our own schema check. The in-server self-test (plugin-testing skill) loads CE and asserts zero `Found … issue(s)` lines for our pack path, and that every expected id exists.

### 11.2 Rough sizing
TFC needs roughly:
- 21×20 rock blocks
- graded ores × 21
- 20×40 wood blocks
- 29 crops × stages
- 214 plants
- 27×60 metal items

That is about 4–5k entries. At 8–15 lines each, the YAML is about 50–75k lines (~2–3 MB). It parses in well under a second (UNVERIFIED) and is cached afterwards. The template expansion per reload is single-threaded per stage. Measure with the `Loaded items in Xms` lines.

## 12. Pitfalls

1. **`enable: false` aborts the parser** (items, blocks, recipes, loot, furniture, images, sounds, …): `return` instead of `continue` [SRC `IdSectionConfigParser.java:72-74`]. Some or all entries of that type never load. If you need to disable something, omit it.
2. Unqualified template references resolve to `minecraft:` (§3.1).
3. The outer argument wins over inner `arguments:`, so inner templates cannot shadow names (§3.4).
4. `overrides` on maps is **shallow** (it replaces whole top-level keys). `merges` are deep, and **lists concatenate** in deep merges and multi-template combination (§3.3).
5. `${…}` anywhere in any id-keyed entry (lore, names, NBT strings, global-variable values) is a placeholder, and a missing argument is an error. Escape with `\$` in plain or single-quoted YAML. Double-quoted YAML treats `\$` as an invalid escape (INFERRED from the YAML 1.2 spec).
6. Defaults are SNBT. Quote strings containing `:`, `.`, `#`, `<`, spaces (§4).
7. Mutually defaulting arguments (`leaves_model` ↔ `leaves_texture`) loop forever if neither is given. INFERRED: StackOverflow → "Unknown error type".
8. `$$` tags with digits or dots corrupt the version. `$$X` means exactly X.0. In merge mode non-map values are silently dropped. `$$fallback` only works when *all* sibling keys are `$$` (§2.1).
9. Any key containing `::` is split (§2.2). An unknown top-level section name is silently ignored (§2.4).
10. TAB auto-fix **rewrites the file** (§2.5).
11. config_factory: lang is not substituted, there is a thread-shared argument map, the instance values are literal, nested factories and templates are ignored, and one bad instance fails the whole factory (§6.2).
12. List and map arguments are shared references, and merges can mutate them (§6.2).
13. `self_increase_int` is stateful per argument object. Counts depend on traversal order and the number of reads.
14. Duplicate ids: the first one in OS file-walk order wins. Ids must be globally unique across packs.
15. Global variables drop the namespace (§7.1).
16. Default slab and stairs templates have only 5 and 4 vanilla bases. Door, trapdoor and gate templates consume the `powered=true` halves of vanilla blocks (§8.1).
17. `default_templates` on disk is frozen at first install and can be edited or disabled by the owner (§8).
18. JSON configs skip `$$`/`::`, and numbers may become `Double` (§2.7).
19. JS has full host access and is runtime-only (§7.4).
20. The reload issue count is not exposed by the API or event. Detect via self-test or a log appender (§9.4).
